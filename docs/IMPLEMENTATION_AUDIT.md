## 1. Итог в одном абзаце

Фундамент ТЗ уже выполнен:
- база на каждую компанию;
- аудит только на добавление, `version` с 409;
- формат ошибок `{error:{code,message,details,request_id}}`;
- деньги — десятичные строки;
- нет физического удаления ключевых данных;
- AI не придумывает числа.

Основной объём работ — **новые сущности и правила продаж**:
1. Отделы, роли «директор» и «РОП», управление сотрудниками. Сейчас права уровня TEAM
   фактически работают как OWN.
2. Типы этапов, причины отказа, история этапов, настраиваемые поля.
3. Итоги и подтверждение встреч, приоритеты и назначение задач.
4. Оплаты как отдельные записи — от них зависит определение «продажи».
5. Планы, рабочие дни и отсутствия.
6. Кабинет РОПа, отчёты и Telegram.

Самые рискованные места:
- принцип «один пользователь — одна компания»;
- валюта и часовой пояс по умолчанию;
- определение «продажи».

Они требуют решения владельца до P0 ([раздел 7](#7-решения-владельца-до-p0)).

| Сверка с «Отчётами дня», «Встречами», «Звонками» 3 дня подряд; открытие ≤ 3 с; читается на смартфоне | приёмка | В нашем backend «Отчётов дня» нет: сверка — с нашими списками встреч, звонков, задач и оплат |

Важные факты из ТЗ РОПа для «Книги определений метрик»:
- В референсе одно и то же «оборот за август» показано двумя числами (2 061 500 и
  2 121 500 сом). Разница — один «финальный» платёж «полная оплата».
- В том же референсе были 63 оплаты без даты, 3 оплаты с датой в будущем, а возвраты не вычитались.

Поэтому у каждой денежной метрики в API будет явная подпись:
- по какой дате считается;
- включена ли полная оплата;
- вычтены ли возвраты.

## 4. Конфликты и безопасный путь

### 4.1 Роли

| ТЗ | Backend сейчас | Frontend сейчас (`lib/permissions/backend-roles.ts`) |
|---|---|---|
| platform_admin | — | ждёт флаг `is_platform_admin` в `/me` |
| company_owner | owner | owner → «Директор» |
| director | — | owner → «Директор» (admin → «Директор», смысл не подтверждён) |
| head_of_sales (РОП) | manager | manager → «РОП» |
| manager / sales_rep | sales_rep | sales_rep → «Менеджер» |
| viewer | viewer | viewer |
| **лидоруб** (ТЗ РОПа: берёт заявки, назначает встречи; план во встречах) | — | — |
| **офис** (ТЗ РОПа: не видит кабинет) | — | — |

Предложение без поломки существующих данных:
1. Добавить роли `director` и `head_of_sales` в `Role`. Существующие значения не переименовывать.
2. Явная таблица соответствия:
   - `owner` = company_owner;
   - `admin` = администратор компании, права как сейчас;
   - `manager` = head_of_sales (переходный синоним, новые РОПы получают `head_of_sales`);
   - `sales_rep` = manager.
3. `is_platform_admin` — флаг пользователя в control plane, межкомпанейский доступ только для
   административных endpoints и с аудитом.
4. Права уровня TEAM начинают работать, когда заполняется отдел (3.1). До этого TEAM = OWN, как сейчас.
5. «Лидоруб» и «офис» из ТЗ РОПа — **отдельные роли или признак функции менеджера?**
   Предложение: роль `lead_caller` с правами менеджера на лиды и встречи и с планом во
   встречах. «Офис» — уточнить у владельца, в основном ТЗ этой роли нет.

### 4.2 Один пользователь — одна компания

- ТЗ требует, чтобы активное членство было одно; после деактивации можно пригласить в другую компанию.
- Сейчас модель допускает несколько членств, и экран frontend `/select-company` на это рассчитан.

Безопасный путь:
- частичный уникальный индекс «одно **активное** членство на пользователя»;
- перед миграцией — отчёт о пользователях с несколькими активными членствами;
- решение по ним принимает владелец, автоматически ничего не деактивируется;
- `/select-company` остаётся для platform_admin.

### 4.3 «Сделка = лид в воронке» во frontend

Frontend открывает сделку «карточкой лида» (`leadDetailSchema`), а ТЗ §4 закрепляет три
сущности. Предложение:
- API карточки — это деталь **сделки** с вложенными клиентом и источником лида;
- лид остаётся отдельной записью до конвертации;
- frontend меняет только источник данных, интерфейс не меняется.

### 4.4 Статусы задач и встреч

| | ТЗ | Frontend | Backend | Предложение |
|---|---|---|---|---|
| Задача | open / completed / cancelled; приоритет low/normal/high/urgent | open / done; high/normal | open / completed | API: open/completed/cancelled, 4 приоритета; frontend отображает `done` = `completed` |
| Встреча | held / no_show / rescheduled / cancelled + подтверждение | scheduled / confirmed / held / no_show / rescheduled / cancelled | scheduled / completed / cancelled | Статус: scheduled/held/no_show/rescheduled/cancelled; подтверждение — отдельное поле (`confirmed_at`), не статус |

### 4.5 Что такое «продажа» и «план»

ТЗ §10 определяет продажу так: уникальный клиент с первым платежом в месяце. Сейчас:
- в backend продажа — сделка `won`;
- платёж — это увеличение `paid_amount` у счёта, отдельной таблицы платежей нет;
- frontend сам отмечает, что план менеджера (оборот) и план РОПа (продажи) — разные метрики.

Безопасный путь:
1. Таблица `Payment` (дата, сумма, валюта, вид prepayment/additional/full, продавец, сделка, клиент, возврат).
2. Существующие `paid_amount` не трогать: вывести из них платежи «без даты» и пометить.
3. Определения — в «Книге определений метрик» до кода кабинета.

### 4.6 Время и валюта

Перевод дефолтов на KGS и Asia/Bishkek меняет:
- результаты KPI за «сегодня»;
- просрочки;
- суммы.

Поэтому порядок такой: сначала настройка компании и тесты границ дня, затем переключение
дефолтов для **новых** записей. Старые суммы не конвертируются.

### 9.4 Что это добавляет к ролям

Инструкции упоминают людей и функции, которых нет ни в backend, ни в основном ТЗ:
- **лидоруб**;
- **опердел** — сопровождение и визы, своя воронка;
- **офис-менеджер**;
- **диспетчер**;
- **руководитель**, который выдаёт логины.

Это нужно учесть в решении по ролям (раздел 7, п. 1 и 6). Предложение: роли компании
`director`, `head_of_sales`, `manager`, `lead_caller`, `operations` (опердел), `office`, `viewer`.
Диспетчер — это право на алерты, а не отдельная роль.
